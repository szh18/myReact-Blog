## 前言

Claude Code 的 Skill 系统允许开发者通过斜杠命令快速调用预定义的工作流程。本文详细介绍两大 Skill 包：

- **superpowers**（obra/superpowers）— 14 个技能，覆盖从需求分析到代码审查的完整开发闭环
- **gstack**（garrytan/gstack）— 49 个技能，Garry Tan 的"虚拟工程团队"，包含浏览器测试、安全审计、自动化部署

---

## 第一部分：superpowers（14 技能）

superpowers 是一套**流程化开发方法论**，每个技能解决开发周期中的一个环节。

### 1. brainstorming — 需求分析

**何时使用：** 开始新功能、创建组件、修改行为之前。

**功能：** 探索用户意图、需求和设计方案，在动手写代码前理清"为什么要做"和"怎么做"。

**示例：**
```
用户：我想给博客加个暗色模式切换
Claude：先调用 brainstorming 技能，分析：
  1. 用户切换暗色模式的触发方式（按钮/系统跟随）
  2. CSS 变量方案 vs 主题文件切换
  3. 是否需要持久化用户偏好
```

### 2. writing-plans — 编写实施计划

**何时使用：** 明确了需求，需要拆分为多步骤执行时。

**功能：** 将需求转化为详细的实施计划，包含步骤、文件清单和验收标准。

**示例：**
```
/brainstorming 完成后 → /writing-plans
生成计划文件，列出：
  1. 添加 CSS 变量定义
  2. 创建 ThemeContext
  3. 修改所有组件引用
  4. 测试验证
```

### 3. subagent-driven-development — 子代理驱动开发

**何时使用：** 实施计划中有多个可并行的独立任务。

**功能：** 将独立任务分派给多个子代理并行执行，然后汇总结果。

**示例：** 同时并行：A 代理改 CSS 变量、B 代理改组件代码、C 代理写测试。

### 4. executing-plans — 执行计划

**何时使用：** 有了书面实施计划后，在新会话中按计划执行。

**功能：** 严格按照计划逐步执行，每完成一步设置审查检查点。

**示例：**
```
/executing-plans
→ 按计划第1步：创建 ThemeContext
→ 审查点：确认 context 结构合理
→ 第2步：改造 App.jsx
→ 审查点：确认主题切换正常
```

### 5. test-driven-development — 测试驱动开发

**何时使用：** 任何功能实现或 Bug 修复，**在写实现代码之前**。

**功能：** 先写失败测试 → 写最小实现让测试通过 → 重构。

这是 superpowers 中约束最严格（rigid）的技能之一，**不可跳过**。

### 6. systematic-debugging — 系统化调试

**何时使用：** 遇到 Bug、测试失败、非预期行为时，**在提出修复方案之前**。

**功能：** 结构化调试流程——复现 → 隔离 → 根因分析 → 修复 → 验证。

### 7. requesting-code-review — 请求代码审查

**何时使用：** 任务完成、实现主要功能、准备合并之前。

**功能：** 提交前自审清单，确认所有需求已满足、测试已通过。

### 8. receiving-code-review — 接收代码审查

**何时使用：** 收到审查反馈后、实施修改建议之前。

**功能：** 技术严谨性验证——不是盲目接受所有建议，而是批判性评估每条反馈。

### 9. verification-before-completion — 完成前验证

**何时使用：** **任何声称"完成了"之前**。

**功能：** 强制运行验证命令（测试、lint、build），确认输出通过后才能宣布完成。**先证据、后结论。**

### 10. finishing-a-development-branch — 收尾分支

**何时使用：** 全部实现完成、测试通过后。

**功能：** 引导选择集成方式——合并到主分支 / 创建 PR / 清理并放弃。

### 11. dispatching-parallel-agents — 并行调度

**何时使用：** 面对 2 个以上独立任务，无共享状态或顺序依赖。

**功能：** 同时启动多个子代理处理独立任务，最大化并行效率。

### 12. writing-skills — 编写新 Skill

**何时使用：** 创建新 Skill 或编辑已有 Skill。

**功能：** 定义 Skill 的触发条件、执行流程和输出格式。

### 13. using-superpowers — 如何使用 superpowers

**何时使用：** **每次对话开始时自动触发**。

**功能：** 告诉 Claude 如何发现和使用其他技能。最核心的"元技能"——要求在任何响应前先检查是否有适用的技能。

**关键规则（来自 skill 文件）：**
> 如果你认为某个技能有哪怕 1% 的可能适用于你正在做的事情，你**必须**调用该技能。这不是可选的。

### 14. using-git-worktrees — Git Worktree 隔离开发

**何时使用：** 需要开发环境隔离的功能开发。

**功能：** 通过 git worktree 创建独立的工作目录，避免污染当前工作区。

## 第二部分：gstack（49 技能）

gstack 是 Garry Tan 的"开源软件工厂"——把单个 AI 助手变成结构化、基于角色的虚拟工程团队。

---

### 二、A. 规划与评审（13 技能）

#### 1. /office-hours — YC 办公时间

**何时使用：** 启动任何新项目或重大功能时。

**功能：** 类似 Y Combinator 的办公时间模式。两种模式：
- **开放模式：** 讨论产品方向和架构决策
- **计划模式：** 深入审查具体计划

**示例：** `/office-hours` → "我想给博客添加全文搜索功能"

#### 2. /plan-ceo-review — CEO 视角评审

**何时使用：** 对任何功能想法进行产品可行性评估。

**功能：** 从 CEO/创始人视角评审——用户价值、市场定位、优先级。

#### 3. /plan-eng-review — 工程架构评审

**何时使用：** 确定技术方案后，写代码前。

**功能：** 工程经理视角——架构合理性、技术选型、可维护性、扩展性。

#### 4. /plan-design-review — 设计评审

**何时使用：** UI 功能规划阶段。

**功能：** 设计师视角——交互逻辑、视觉一致性、可用性。

#### 5. /plan-devex-review — 开发体验评审

**何时使用：** 开发工具和流程改进时。

**功能：** 审查开发体验——CI/CD 效率、开发环境、代码生成质量。

#### 6. /plan-tune — 自调优

**何时使用：** 调整 gstack 行为偏好。

**功能：** 根据开发者心理画像自动调整问题灵敏度。

#### 7. /autoplan — 自动全流程评审

**何时使用：** 想做完整的自动评审链条。

**功能：** 依次运行 CEO → 设计 → 工程 → DX 四个评审，自动做出决策。

#### 8. /design-consultation — 设计咨询

**何时使用：** 需要完整的设计系统方案。

**功能：** 理解产品 → 研究竞品 → 提出完整设计系统（美学、字体、颜色、布局、间距、动效）。

#### 9. /design-shotgun — 设计散弹枪

**何时使用：** 需要快速出多个设计方案对比。

**功能：** 生成多个 AI 设计变体 → 打开对比板 → 收集反馈 → 迭代。

#### 10. /design-html — 设计落地

**何时使用：** 设计确认后。

**功能：** 将设计转化为生产质量的 HTML/CSS。

#### 11. /design-review — 设计审查

**何时使用：** UI 实现完成后。

**功能：** 设计师视角 QA——视觉不一致、间距问题、层级问题、AI 设计缺陷。

#### 12. /devex-review — 开发体验审计

**何时使用：** 功能开发完成后。

**功能：** 实时 DX 审计——检查开发流程中的摩擦点。

#### 13. /document-generate — 生成文档

**何时使用：** 缺少文档时。

**功能：** 从零生成功能、模块或整个项目的文档。

---

### 二、B. 开发与实施（5 技能）

#### 14. /review — 代码审查

**何时使用：** 提交 PR 前。

**功能：** 全面的前置审查——代码质量、测试覆盖、潜在 Bug、性能隐患。

#### 15. /cso — 首席安全官

**何时使用：** 涉及用户输入、API 调用、认证逻辑时。

**功能：** OWASP Top 10 + STRIDE 威胁建模全面安全审计。

#### 16. /investigate — 调查问题

**何时使用：** 遇到不明原因的 Bug。

**功能：** 系统化根因调查——日志分析、代码追踪、假设验证。

#### 17. /pair-agent — 双代理协作

**何时使用：** 需要第二个 AI 视角时。

**功能：** 生成一次性密钥，让远程浏览器 AI 代理加入协作。

#### 18. /skillify — 技能化

**何时使用：** 发现可复用的工作模式时。

**功能：** 将最近成功的 `/scrape` 操作固化为永久技能。

---

### 二、C. 测试与质量（5 技能）

#### 19. /qa — 完整 QA 测试

**何时使用：** 部署到 staging 后。

**功能：** 系统化 QA——打开真实浏览器、导航页面、验证元素状态、对比前后截图、测试响应式布局。

#### 20. /qa-only — 仅报告 QA

**何时使用：** 只需测试报告，不需自动修复。

**功能：** 与 `/qa` 相同但不自动修复发现的问题。

#### 21. /benchmark — 性能基准

**何时使用：** 部署前后对比性能。

**功能：** 使用浏览器守护进程进行性能回归检测。

#### 22. /benchmark-models — 模型基准

**何时使用：** 对比不同 AI 模型效果。

**功能：** 跨模型的 gstack 技能基准测试。

#### 23. /canary — 金丝雀监控

**何时使用：** 部署后监控。

**功能：** 部署后的金丝雀监控——检测异常、回滚警报。

---

### 二、D. 发布与部署（6 技能）

#### 24. /ship — 打包发布

**何时使用：** 功能完成、测试通过、准备发布。

**功能：** 自动检测基础分支 → 运行测试 → 审查 diff → 更新版本号 → 更新 CHANGELOG → commit → push → 创建 PR。

这是 gstack 最核心的技能之一。

#### 25. /land-and-deploy — 部署上线

**何时使用：** PR 合并后。

**功能：** 完整的部署工作流——合并到部署分支、触发 CI/CD、验证部署状态。

#### 26. /landing-report — 部署报告

**何时使用：** 查看部署队列状态。

**功能：** 只读队列仪表盘，显示各 VERSION 槽位的状态。

#### 27. /setup-deploy — 配置部署

**何时使用：** 首次配置部署流程。

**功能：** 为 `/land-and-deploy` 配置部署设置。

#### 28. /document-release — 发布文档

**何时使用：** 版本发布后。

**功能：** 更新文档以反映最新发布的变化。

#### 29. /make-pdf — 生成 PDF

**何时使用：** 需要 PDF 格式的文档。

**功能：** 将任何 Markdown 文件转为出版级质量的 PDF。

---

### 二、E. 浏览器操作（6 技能）

#### 30. /browse — 浏览器控制

**何时使用：** 需要测试页面、截图、验证部署。

**功能：** 快速无头浏览器（基于 Playwright Chromium），支持 75+ 命令：

| 类别 | 命令示例 |
|------|---------|
| 导航 | `browse navigate <url>` |
| 交互 | `browse click <sel>`、`browse fill <sel> <value>` |
| 检查 | `browse attrs <sel>`、`browse css <sel> <prop>` |
| 截图 | `browse screenshot` |
| 抓取 | `browse scrape <images\|videos>` |
| 性能 | `browse perf` |

#### 31. /open-gstack-browser — 打开浏览器

**何时使用：** 需要可视化浏览器操作。

**功能：** 启动 AI 控制的 Chromium，侧边栏集成扩展。

#### 32. /scrape — 网页抓取

**何时使用：** 从网页提取数据。

**功能：** 首次调用原型化流程，后续调用执行稳定的抓取流水线。

#### 33. /setup-browser-cookies — 配置浏览器 Cookie

**何时使用：** 需要登录态访问网站。

**功能：** 从真实 Chromium 浏览器导入 Cookie 到无头浏览会话。

#### 34. /connect-chrome — 连接 Chrome

**何时使用：** 连接已有浏览器实例。

**功能：** 连接到正在运行的 Chrome 实例。

### 二、F. 上下文与记忆（5 技能）

#### 35. /context-save — 保存上下文

**何时使用：** 长对话中定期保存。

**功能：** 保存当前工作上下文（包括决策、代码片段、TODO），防止上下文窗口溢出丢失信息。

#### 36. /context-restore — 恢复上下文

**何时使用：** 新会话开始、或上下文被截断后。

**功能：** 恢复之前 `/context-save` 保存的上下文。

#### 37. /learn — 经验学习

**何时使用：** 遇到值得记录的教训。

**功能：** 管理项目经验库——记录问题、解决方案和最佳实践。

#### 38. /retro — 回顾总结

**何时使用：** 每周或里程碑结束时。

**功能：** 工程回顾——分析本周工作、识别改进点、记录经验。

#### 39. /sync-gbrain — 同步知识库

**何时使用：** 代码变更后。

**功能：** 保持 gbrain 与代码仓库同步，更新搜索索引。

### 二、G. 安全防护（4 技能）

#### 40. /careful — 谨慎模式

**何时使用：** 处理生产环境、敏感数据时。

**功能：** 拦截 `rm -rf`、`DROP TABLE`、`git push --force` 等危险命令，需要确认才执行。

#### 41. /guard — 完全防护模式

**何时使用：** 高风险操作时。

**功能：** 谨慎模式 + 文件编辑限制（仅允许指定目录内的编辑）。

#### 42. /freeze — 冻结代码基

**何时使用：** 需要暂时保护某目录不被修改。

**功能：** 将文件编辑限制到指定目录。

#### 43. /unfreeze — 解冻

**何时使用：** 解除冻结限制。

**功能：** 清除 `/freeze` 设置的边界。

### 二、H. 集成与基础设施（6 技能）

#### 44. /claude — Claude Code 集成

**何时使用：** 在非 Claude Code 环境中调用。

**功能：** Claude Code CLI 包装器，支持三种模式（交互/非交互/子代理）。

#### 45. /codex — Codex 集成

**何时使用：** 使用 OpenAI Codex 时。

**功能：** OpenAI Codex CLI 包装器，同样三种模式。

#### 46. /health — 代码健康仪表盘

**何时使用：** 定期检查项目健康。

**功能：** 代码质量仪表盘——复杂度、重复率、覆盖率等指标。

#### 47. /gstack — gstack 主技能

**何时使用：** 首次使用 gstack。

**功能：** 初始化 gstack 环境变量、会话管理、遥测配置（可选关闭）。

#### 48. /gstack-upgrade — 升级 gstack

**何时使用：** 定期更新到最新版。

**功能：** 检测全局 vs 本地安装，自动拉取最新代码并重新生成技能文档。

#### 49. /setup-gbrain — 配置知识库

**何时使用：** 首次配置 gbrain。

**功能：** 安装 CLI → 初始化本地 PGLite 或 Supabase → 注册 MCP → 信任策略。

## 第三部分：前端开发实战流程

### 场景：给博客加搜索功能

```
1. /office-hours          → 讨论搜索方案（fuse.js vs 后端搜索）
2. /brainstorming         → 分析用户需求：输入框、结果页、高亮
3. /writing-plans          → 编写计划：组件 → hook → 页面 → 样式
4. /plan-eng-review        → 审查架构：fuse.js threshold、keys 配置
5. /test-driven-development → 先写测试、再写实现
6. /review                 → 代码审查：覆盖度、边界情况
7. /design-review          → 视觉审查：搜索框样式、结果卡片
8. /qa                     → 浏览器测试：输入、跳转、空状态
9. /ship                   → 自动打包发布
```

### 场景：发现线上 Bug

```
1. /systematic-debugging   → 复现 → 隔离 → 根因分析
2. /investigate            → 日志分析、代码追踪
3. /freeze                 → 冻结代码基，只允许修改 Bug 相关文件
4. 修复 → 测试验证
5. /unfreeze               → 解冻
6. /verification-before-completion → 确认修复有效
7. /ship                   → 发布修复
```

## 第四部分：注意事项

### DeepSeek 兼容性

当前环境使用 DeepSeek-v4-pro 作为后端，大部分 Skill 可以正常工作，但以下功能可能受限：

- `/browse` 浏览器相关功能依赖 Playwright Chromium（已安装）
- 部分 gstack 技能依赖 `bun` 运行时（已安装）
- superpowers 的 Skill 工具调用机制在 DeepSeek 上可能需要额外适配

### 性能考虑

- gstack 的 49 个技能每个都是完整的 Markdown 文档，总计约 **65 万 tokens**
- 每次调用技能时会加载对应文档，建议在需要时才调用
- 长对话中善用 `/context-save` 和 `/context-restore`

### 定期维护

```bash
# 更新 gstack
/gstack-upgrade

# 更新 superpowers（手动）
git -C ~/.claude/skills/gstack pull
```

## 总结

| 维度 | superpowers | gstack |
|------|-------------|--------|
| 技能数量 | 14 | 49 |
| 定位 | 流程方法论 | 虚拟工程团队 |
| 核心优势 | 严谨的开发闭环 | 完整的工具生态 |
| 适用场景 | 日常开发流程 | 全生命周期管理 |
| 学习曲线 | 低（14个技能） | 中高（49个技能） |

**建��使用顺序：** 先掌握 superpowers 的 14 个技能作为基础工作流，再逐步引入 gstack 的高级功能（浏览器测试、安全审计、自动化部署）。
